## 定位：“[渲染层错误] undefined is not iterable (Array.from)” 的真凶是微信基础库 wx-touchtrack

排查方法（可复用）：
- 基础库包：`~/Library/Application Support/微信开发者工具/<hash>/WeappVendor/3.1.5.wxvpkg`，是自定义容器但**内容未压缩**：头部 4B 文件数，之后每条 `[4B nameLen][name][4B offset][4B size]`，offset 连续。
- 用 node 读该包，找到 `/WAWebview.js` 的 `[offset,size]`，取出文本后按报错栈里的 `1:<col>` 切片即可看到源码。
- 本次：WAWebview.js 内容 offset=9537630、size=2723756（3.1.5，hash 目录 d1e8765721a6c23d43b14c95b1843e6b）。

结论：报错在 `exparser.registerBehavior({is:"wx-touchtrack"...})` 里，
`d = e => l && Array.from(e.touches).some(e => e.identifier === l.identifier)`（列 712020），
调用点是 touchend 监听器（列 712483 `if(l && d(e))`）——即 `e.touches === undefined` 的合成事件。
- `wx-touchtrack` 被内置 `scroll-view` / `movable-view` / `picker-view` / `slider` / `swiper` 使用（本项目只用到 scroll-view）。
- 栈外层 `W`（列 806502）在开发者工具的鼠标→触摸事件注入代码里（`__wxGetRelativeCoordinates`、`_requireActive`），即事件是开发者工具模拟出来的，真机触摸事件必带 `touches`，故判断为**开发者工具/基础库问题**，非业务代码问题。
- 与“新尺寸才报错”的关联：弹层列表内容（4 个尺寸 ≈ 810px）现在超过固定 713px，要滚到第 4 个（新尺寸）才能点，滚动（拖拽）在 scroll-view 内触发该 bug；旧尺寸不用滚，所以正常。
- 备选规避方案（未实施，需真机验证）：把弹层 `<ScrollView>` 换成 `<View style="overflow-y:auto">`，绕过 wx-touchtrack。

现象：刷新页面时 `Failed to load resource: 500`，接着 `ENGINE_WASM.js: Uncaught (in promise) RuntimeError: Aborted(both async and sync fetching of the wasm failed)`、`draco_mini.js: Aborted(undefined)`。

证据（开发者工具自身日志 `~/Library/Application Support/微信开发者工具/<hash>/WeappLog/logs/*.log`）：

- 项目里没有任何 `__dev__` 引用；错误从 2026-09-14 15:21（首次编译/打开）就存在，与业务改动无关。

- 影响面：仅 3D 模型（产品详情页 xr-model-viewer），且仅开发者工具；真机由客户端内置引擎提供。
- 处理建议：重启开发者工具 / 清缓存；检查代理（机器上装了 Clash Verge，可能拦了资源下载）；把调试基础库从 3.1.5 换成 3.16.3 / 3.17.2；必要时删 `WeappVendor` 重新下载；真机验证。

### 纠正：真正的根因是开发者工具的路由 bug（与基础库版本无关）
用户已手动切到 3.17.2（日志 `10:17:32 makeSureVendorDownloaded start version=3.17.2`），仍报错。读开发者工具 app.asar 源码后确认：
- `__dev__` 专用路由只匹配**绝对路径**：`if(!href.startsWith("/__dev__/")&&!href.startsWith("/__alphadev__/")) return;`。
- xr-frame 引擎的 `<script>` 由 `if(useXRFrame){["ENGINE_WASM.js","draco_mini.js"]}` 注入（绝对路径 `/__dev__/xxx.js`，能正常 200），但引擎内部用**相对路径**加载 wasm，实际请求变成 `/appservice/__dev__/ENGINE_WASM.wasm`、`/appservice/__dev__/draco_decoder.wasm` → 不走专用路由 → 走兜底 `dealSimulatorRequest` → 去**项目目录**找 → `ENOENT` → 500。
- 开发者工具自带这些文件（app.asar 里 `/js/vendor/{ENGINE_WASM.js,ENGINE_WASM.wasm,draco_mini.js,draco_decoder.wasm}`，offsets 116366517/116409428/116308004/116022257，dataStart=16+jsonSize 再 4 字节对齐）。

已做的临时修复（未进 git，dist/ 已 gitignore）：用 node 从 app.asar 按 offset 提取这 4 个文件到 `dist/weapp/__dev__/`，兜底代理就能命中该路径。注意全新编译/清缓存可能清掉 dist，需要重新执行；正规做法是换稳定版/更新的开发者工具。

**验证结果：用户确认"现在好了"，3D 预览恢复正常**（2026-09-15）。若 dist 被清掉，重新执行提取即可；如需长期稳定，可加 `npm run xr-engine:patch`（从 `app.asar` 的 `/js/vendor/` 提取到 `dist/weapp/__dev__/`）。

### 追加：为什么会复发 + "以前没问题"的原因
1. **复发**：Taro 构建会清理/重建输出目录，`dist/weapp/__dev__/` 被删掉（已实测该目录在用户重新构建后消失）。手工放置只是临时兜底，需要每次构建后重放；要长期稳定应走 `copy.patterns` + `.wx-dev-engine/` 缓存目录或 npm script。
2. **"以前没问题"**：开发者工具本体在 **2026-09-07 17:41 更新过**（`/Applications/wechatwebdevtools.app/Contents/Resources/app.asar` 时间戳），当前构建 `2.02.2608040` 是这次更新后的版本，正是它把 `/appservice/__dev__/*` 的静态路由丢了 → 属于新版本的回归，不是我们代码或基础库的问题。回退/换稳定版开发者工具即可根治。
3. **体积提醒**：`dist/weapp` 主包当前约 2.32MB（不含 pages-sub、不含 .map），再把 2.9MB 引擎文件放进主包目录会导致预览/上传超限；若要长期保留，需在 `project.config.json` 的 `packOptions.ignore` 里排除 `__dev__`（但需验证开发者工具模拟器是否仍能读到该目录）。

用户把开发者工具换成 **2.01.2510290（更新时间 2026/03/25）** 后 3D 预览恢复正常 → 证实是 2.02.2608040（2026-09-07 更新）引入的回归。
